TL;DR

Your model reads a document and fills in a form. It writes a figure that is almost what the page says. Nothing flags it, and it flows into a decision. quotebound makes that impossible to write: every extracted value is copied from the source, and every place the model wanted to stray is flagged for review.

The extraction problem nobody budgets for

  • Models "improve" values. They join wrapped text, complete truncated names, round numbers and drop digits. On our receipts test a well-trained model scored 95 F1 and still did all of this: 5 values that are not on the receipt, one with a digit dropped.
  • Valid JSON is not a correct value. Schema-constrained decoding guarantees the shape of the answer, not where its values came from.
  • Reviewers can't tell which values to check. Nothing marks the risky ones, so people re-read every document, and the savings from automation disappear.
  • Output that changes between runs fails an audit. A speed-up, a batch size or a quantised model can quietly change the answer.
  • Sensitive documents can't go to a cloud API. Payslips, medical letters and identity documents need to stay on your own hardware.

01Shape is not content

A common job for a small language model is to read free text and pull values out of it: the total on a receipt, the dates in a booking request, the figures in a case note. For some of these jobs a wrong value is far worse than a missing one. A total that is off by a digit, or a name the model "corrected", can flow into a decision unnoticed. A missing value at least gets noticed.

Constrained decoding is the usual answer to "make the model's output valid", and it is a good one. Libraries and inference servers can hold a model to a JSON Schema or a grammar, so every answer parses and has the right fields. But a schema constrains the shape of the answer, not its content. Under a schema, "total": "111,000" and "total": "111,900" are equally valid strings. Nothing ties the value to the document it came from.

A prompt that says "only copy values from the text" helps, but it is a request, not a guarantee. quotebound makes it a guarantee for the values that need one.

02Bind quotes to the input

In quotebound's schemas, some strings are quotes. A string is a quote when its key is named quote, or when it is a $ref to a definition named quote. With --quote-source user, the decoder lets the model write a quote only if it is a stretch of the user's message. The model still chooses which stretch, where it starts and where it stops. What it cannot do is write a quote that is not there.

{
  "type": "object", "additionalProperties": false,
  "required": ["items", "total"],
  "properties": {
    "items": {"type": "array", "items": {
      "type": "object", "additionalProperties": false, "required": ["name", "price"],
      "properties": {"name": {"$ref": "#/$defs/quote"}, "price": {"$ref": "#/$defs/maybe"}}}},
    "total": {"$ref": "#/$defs/maybe"}
  },
  "$defs": {
    "quote": {"type": "string", "minLength": 1, "maxLength": 80},
    "maybe": {"anyOf": [{"$ref": "#/$defs/quote"}, {"type": "null"}]}
  }
}

A quote also has to stand alone: it cannot start or end inside a word, so "utdoor" cannot be cut from outdoor. A number cannot be cut out of a wider one, so "2" cannot come from 2.00, "000" cannot come from 60.000, and "33" cannot come from 33%. Quotes have no white space at either end. ASCII letter case is ignored when matching, so a quote may differ from the source in case, and only in case.

The guarantee is narrow and exact: every quote is a stretch of the input that stands alone. It does not promise that the model picked the right stretch. That is what training and evaluation are for, and what the override log helps with.

04Architecture

quotebound is one C++ binary with two commands, train and generate. Both share a tokenizer and a model. Everything runs on MLX's C++ API and Metal, and nothing runs in Python. The schema constraint is also built as a separate C library, so other decoders can use it.

Tokenizersrc/unicode · pretokenize · tokenizer
Byte-level BPE with Qwen's split patterns and chat templates. Its output is checked token for token against Hugging Face tokenizers.
Modelsrc/model · deltanet
The Qwen3 and Qwen3.5 forward pass: attention, Gated DeltaNet, KV cache and the LoRA path. Checked against mlx-lm on real checkpoints.
Trainersrc/data · loss · delta_grad · lora · adamw · train
Batch plans, chunked loss, a custom gradient for the recurrence, AdamW, and checkpoints with exact resume.
Decodersrc/generate · batch
Prefill and greedy decoding, one prompt or a batch file, with resume, timings and confidences.
Constraint enginesrc/schema · constrain
Compiles the schema to a byte automaton, walks the token trie, and binds quotes through the suffix array.
Exact draftssrc/draft · exact
Free draft tokens, and a verify pass whose every row rounds exactly like a one-token step.
C librarysrc/constrain_capi
The constraint behind a C interface with no MLX, built for macOS or Linux.
Files and provenancesrc/files.h · provenance
Synced writes and the deny-list. Adapters record the checkpoint they were trained on and refuse any other.

05How the constraint works

At every decoding step the decoder asks one question: which tokens may come next? It takes the model's argmax over those tokens only. An answer the model would have written validly anyway comes out the same, token for token. Three structures answer the question together.

The schema as a byte automaton

The schema compiles to a pushdown automaton over the bytes of compact JSON, the form json.dumps(v, ensure_ascii=False, separators=(",", ":")) writes. A state is a small set of configurations, one per live anyOf alternative, each a stack of open values. The automaton tracks:

  • which keys an object has written, so required keys come before it closes and no key repeats;
  • enums and consts, array lengths, and unique items;
  • string lengths in code points, and a pattern's character class;
  • numbers within a fixed number of digits, so they read back finite.

Every schema keyword that is read is listed in src/schema.h. Any other keyword is refused by name, with its location, so a schema never quietly means less than it says.

The vocabulary as a trie

Every token's bytes go into one trie: about 248,000 tokens and 590,000 nodes for Qwen3.5, built in about 50 ms. To find the allowed tokens, the decoder walks the trie from the automaton's current state and prunes every subtree whose bytes the automaton refuses. Free strings are the expensive case, because almost every token is legal inside one. For those, a table is precomputed once per character class: which tokens stay inside the string, and what each leaves pending. In the test suite this makes a free-string step take 0.44 ms instead of the walk's 5.96 ms. Averaged over a structured answer, choosing the allowed set takes about 0.015 ms a step.

The budget

The automaton knows the fewest bytes that close the answer from any state. A token is allowed only if the answer can still be closed, and stopped, within the remaining token budget. So an answer that runs long is closed by the shortest valid path instead of being cut off mid-string. A stop token is allowed only once the JSON is complete.

Quotes: a suffix array, narrowed byte by byte

The message is written as a JSON string body, with ASCII letters lower-cased. Every byte offset where a quote may start is collected, meaning an offset that does not split a word or a number. These offsets are sorted by the bytes that follow them: a suffix array. Two side tables record where a quote may end.

A quote in progress is then just a range [lo, hi) of that sorted array: the start offsets whose text begins with the bytes written so far. Each new byte narrows the range with two binary searches. A byte is allowed only if:

  • the range stays non-empty;
  • some start in it can still reach a valid end within the string's maxLength.

The closing quote mark is allowed only where one of the starts ends on a boundary.

Because the check runs on bytes, it does not matter how the tokenizer splits the quote. Any token whose bytes keep the range alive is allowed, wherever its boundaries fall.

The same rule outside the Mac

The constraint does not depend on MLX. make constrain-lib builds it as a small C library, libquotebound_constrain. It also builds on Linux. A decoder written for another runtime, a CUDA server for example, can then mask its logits with exactly the tokens quotebound allows. Two decoders that share it can differ only in the model's arithmetic, never in what an answer may be.

06Overrides: where the model wanted to stray

The decoder keeps each step's unconstrained argmax as well. When the constrained choice differs, it records an override: the step, and the byte span of the answer that the decoder, not the model, chose. The argmaxes are queued beside the steps and read at the end, so recording costs the decoder no extra wait.

An override is a precise, free signal: here, the model wanted to write something the input does not support. The receipts recipe shows how precise. We ran the same fine-tuned adapter on 96 test receipts twice, with the constraint and without it:

  • Without the constraint, it wrote 5 values that are not on the receipt.
  • With the constraint, it was overridden at 5 steps, in 4 answers. These were the same 4 receipts and the same 5 values.

None of the five matches the dataset's reference values, so the two runs score the same. The difference is in what a caller can trust. Constrained, every value is the receipt's own text, and the five places where the model pulled away are marked. A pipeline that withholds overridden values would have withheld exactly those five and nothing else. On SQuAD it is the same story: the fine-tuned model was overridden in one answer of 300, and that answer was wrong.

Example B in section 03 follows the digit-dropped case through to the row a caller receives.

--token-confidence adds each token's log-probability and its top-two margin over the whole vocabulary, taken before the mask. That gives a second, softer signal beside the overrides.

07Speculative decoding that changes no byte

Decoding one token at a time on a Mac is limited by memory bandwidth: every step reads every weight. Speculative decoding guesses several tokens ahead and checks them all in one pass, so the weights are read once for several tokens. In most implementations, though, the check pass is not bit-for-bit the same computation as a one-token step. A matrix multiply over many rows sums in a different order from a matrix-vector multiply over one row. A different order rounds differently, and on a near-tie a different rounding flips the argmax. The output is "almost always" the same.

For a pipeline that must be reproducible, "almost always" isn't enough. quotebound's check pass is built so that each row equals the one-token step bit for bit.

  • Projections run through a GEMV kernel adapted from MLX's own. It holds V vectors where MLX's holds one. Each lane splits the inner dimension the same way, adds its products in the same order, and reduces with the same shuffles. Each tile of the weight matrix is loaded once and applied to every vector before the next tile is read. So the bandwidth saving is real and the arithmetic is unchanged.
  • Attention runs each row on its own, over the keys up to it, as its decode step would. So does the recurrent layers' convolution window.
  • The Gated DeltaNet state advances one step at a time, and every row's state is kept. When a draft is rejected, the caches are cut back to the last accepted row.
  • LoRA adapters are applied unmerged, through the same low-rank path in float32 that the one-token step uses.

The drafts themselves cost no model call. Prompt lookup uses the tokens that followed the latest earlier occurrence of the current context, which works well because quotes are copied from the prompt. An n-gram table of the training set's answers covers the keys, punctuation and enum values the model writes every time. A wrong guess costs a little verify work, never a different answer.

Two flags trade exactness for speed, and are documented as inexact. --merge-lora folds the adapter into the bf16 weights, and rounding the merged weights once can change answers. --quantize 8 runs 8-bit weights. Neither is used for any number on this page.

08Fine-tuning Qwen3.5 locally

Qwen3.5 is a hybrid model. Most of its layers are Gated DeltaNet layers, a recurrence with a matrix-valued state per head, and the rest are full attention. MLX ships a fast forward kernel for the recurrence, but training needs its gradient. quotebound supplies it through mx::custom_vjp:

  • The forward is unchanged: the model's own call to MLX's recurrence op, in float32. The training forward equals inference without a cache, bit for bit.
  • Checkpoints. The state is saved at every 64th step. These are the forward's own bits, because the op gives the same bits for any split into chunks of 16 steps or more.
  • A Metal kernel for the backward. For each chunk, last first, the kernel replays the chunk from its saved start and walks it backwards. It keeps the start of every 8 steps in registers, so no per-step state ever goes to memory. One simdgroup owns one row of the state, as in the forward kernel.
  • Deterministic sums. Gradients that sum over rows are reduced in threadgroup memory in a fixed order, with no atomics. Atomics would be faster, but their sums depend on scheduling, and a deterministic gradient is what makes a resumed run match an uninterrupted one bit for bit.

The kernel's gradients are checked against autodiff through plain MLX ops, and the forward against mlx-lm's kernel. Around it sit the usual pieces:

  • LoRA on the attention, DeltaNet and MLP projections, with rank 16 and alpha 32 by default;
  • per-layer activation checkpointing;
  • cross-entropy computed 256 positions at a time over the 248,320-token vocabulary;
  • AdamW as PyTorch defines it, with warmup and a cosine schedule;
  • checkpoints that resume exactly, and adapters that refuse to load on a different base checkpoint or chat template.

11Limits

  • Apple silicon only, on macOS 26 with the mlx 0.32.3 wheel. The C constraint library is the only part that builds on Linux.
  • Qwen3.5 and Qwen3 text models only. Qwen3.5-4B and 9B are tested against mlx-lm on real checkpoints. Qwen3 is tested on its tokenizer, its chat template and tiny random models.
  • LoRA on a bf16 base. No full fine-tuning and no quantised training.
  • Greedy decoding, one sequence at a time.
  • A practical subset of JSON Schema. Anything outside it is refused by name, never ignored.
  • The quote rule binds values to the input's text. It cannot tell whether the model chose the right stretch.
  • Each recipe was run once, on one machine.
